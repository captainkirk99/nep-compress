# V1.2.0 Sprint 5: Clarify LZ4 Plugin Questions

Source: docs/roadmap.md, "V1.2.0 Compression Filter for Meteosat / Sprint 5".

## Goal

The roadmap asks three questions. This plan answers them and fixes
what the answers show:

- **Does nep-compress ship its own LZ4 plugin?** Yes.
- **Does it differ from hdf5_plugins?** Yes. It is a fork that
  reinterprets `cd_values[0]`.
- **Which is correct?** HDF Group `hdf5_plugins` `master`, which matches
  the registered definition of filter 32004.

After this sprint, nep-compress ships the upstream plugin source
unchanged (only comments and the HDF Group license notice are added).
Every 32004 file nep-compress writes then means the same thing to any
32004 provider, including hdf5plugin, the HDF Group builds and conda's
`hdf5-external-filter-plugins-lz4`. `nc_def_var_lz4(ncid, varid,
level)` keeps its signature and meaning (LZ4 acceleration 1-9), but
stores the standard two-parameter form `{0, 1 - level}`.
`nc_inq_var_lz4` reads both the new form and the old one-parameter
form. CI compares the plugin against an independent provider and fails
if files bloat.

## Decisions

| Topic | Decision |
|---|---|
| Direction (Q1) | Follow upstream. Vendor `HDFGroup/hdf5_plugins` `master` `LZ4/src/H5Zlz4.c`. `cd_values[0]` is the block size (0 = default 1 GiB) and `cd_values[1]` is the encoder selector. |
| Stored parameters | `nc_def_var_lz4(level)` stores 2 parameters: `{0, (unsigned int)(1 - level)}`. Level 1 is stored as `{0, 0}` and level 9 as `{0, 4294967288}`. The level keeps its meaning (LZ4 fast-mode acceleration). |
| Inquiry (Q2) | `nc_inq_var_lz4` accepts both forms. With 1 parameter, the value is returned as the level, unchanged (the legacy nep form, which is ambiguous with hdf5plugin's `(nbytes,)`). With 2 parameters, the level is decoded from `cd_values[1]`: 0 or 1 gives 1; a negative value `e` gives `1 - e` if that is in 2-9; anything else (LZ4HC ≥ 2, or acceleration > 9) returns `NC_EFILTER`. Any other parameter count returns `NC_EFILTER`. `cd_values[0]` is ignored. |
| LZ4HC (Q3) | Not this sprint. The API is unchanged (see Out of scope). |
| Release (Q4) | Ships in 1.2.0, which is not tagged yet (tags: `v1.0.0`, `v1.1.0`). SOVERSION stays 1 and no signatures change. The release notes describe the change in stored parameters and the encoding hazard of files written by older versions. |
| Vendoring (Q5) | Upstream file byte-for-byte, except added comments: Doxygen blocks and a header naming the upstream commit and pointing to the HDF Group notice. Upstream's `printf` on a decompression size mismatch is accepted. Provenance goes in a new `plugins/README.md`. The HDF Group notice goes in a new `plugins/COPYING.hdf5_plugins`, which is installed. |
| CI comparison | Set `NEPCOMPRESS_REFERENCE_LZ4_PLUGIN_DIR` to hdf5plugin's `PLUGINS_PATH` in every LZ4 job, so the existing cross-provider tests run. Add size tests that fail on block-size bloat. |
| Upstream pin | `HDFGroup/hdf5_plugins` `master` = `4d6b8cec9263cf4b328a671cc85239fd058541b7` (2026-10-29, "Fix snapshot release (#298)"). Checked with `gh api .../compare/4d6b8ce...master`: identical, ahead_by=0. |

## Current state (2026-10-30)

Answers to the roadmap questions, all verified locally:

1. **nep-compress ships its own plugin.** `plugins/H5Zlz4.c` (309
   lines) and `plugins/lz4_config.h` (a config shim, Ed's) are built by
   `CMakeLists.txt` as the `h5lz4` MODULE target. The output is
   `build/plugin/libh5lz4.so`, installed to `${CMAKE_INSTALL_LIBDIR}/plugin`.
   Conda installs it as `lib/hdf5/plugin/libh5lz4_nepcompress.so`
   (`conda/recipe/build.sh`).
2. **It is a fork of Ed's `hdf5_plugins` fork, branch `origin/e1`.**
   The fork is in `/home/ed/hdf5_plugins`; the roadmap's
   `/fast/ed/hdf5_plugins` does not exist. Commit `bcb40e0` (Ed,
   2025-09-12, "fixed plugin", not in `master`) made these changes
   against upstream:
   - `cd_values[0]` became the LZ4 **acceleration**. Upstream has always
     used it as the **block size** (checked at `01a8338` 2017,
     `efa127e` 2019, `5908c83` 2023, `2cd2322` 2025 and the current
     `master`).
   - `H5Z_filter_lz4` became non-static.
   - The decompression `printf` was commented out.

   nep-compress's copy is that file plus Doxygen comments (`git diff`
   against upstream shows nothing else).
3. **Upstream `master` has moved on since the fork.**
   - `6a04fd5` (Neil Fortner, 2026-05-01) sets `*buf_size =
     origSize` on decode. Our copy leaves `*buf_size` stale. No failure
     has been seen in ctest or the ASan job, so the effect is unproven
     but the fix is correct.
   - `c00fb8d` (#267, 2026-07-10) adds the encoder selector
     `cd_values[1]`: ≥ 2 is LZ4HC at that level (clamped to 12); 0 or 1
     is the default fast encoder; a negative value is acceleration
     `1 - value`. It also adds output-size overflow guards
     (`LZ4_compressBound` ≤ 0, `nBlocks * perBlock` wrap). It needs
     `lz4hc.h` from liblz4 (present at `/usr/include/lz4hc.h`; it is
     part of the same `liblz4` that Spack `lz4` and conda `lz4-c`
     provide).
   - `H5Z_filter_lz4` is static again.
   - The decompression `printf` is active.
   - The on-disk chunk format is unchanged. `plugins/LZ4_HDF5_format.md`
     is identical to upstream `LZ4/LZ4_HDF5_format.md`.
4. **Upstream is the correct one.**
   - The registered definition, `docs/RegisteredFilterPlugins.md` in
     upstream ("Plugin ID 32004"), says: `[0]` is the block size, up to
     2,113,929,216, default 1 GiB; `[1]` is the encoder selector.
   - hdf5plugin (`src/hdf5plugin/_filters.py`, class `LZ4`) writes
     `filter_options=(nbytes,)`, with 0 meaning 1 GiB.
5. **Files decode in both directions; the problem is encoding.** The
   block size is stored in each chunk header, so either plugin decodes
   the other's files. Measured in `/tmp/lz4probe.skge` with 1 Mi
   floats (4 MiB raw, 65536-element chunks) and `nc_def_var_lz4`:

   | Writer plugin | level 1 | level 9 |
   |---|---|---|
   | nep-compress `build/plugin` | 89,104 B | 89,101 B |
   | `/usr/local/netcdf-c/hdf5/lib/plugin/libh5lz4.so` (Sep 2025) | 89,104 B | 89,101 B |
   | upstream `master` built locally | 20,979,952 B | 6,066,928 B |

   With a standard provider loaded, `nc_def_var_lz4` makes files 1.5x
   to 5x **larger than raw**, because the level is taken as the block
   size in bytes. `nccopy` of a nep-written `32004,9` file through the
   upstream plugin also gives 6,066,928 B. All round trips were
   bit-exact. The `/usr/local` build behaves like nep-compress, so it
   was probably built from `e1`. It is therefore not an independent
   reference.
6. **There is no license notice.** Upstream `COPYING` ("Copyright (c)
   2017, The HDF Group", BSD-style, condition 1: retain the notice in
   source; condition 2: reproduce it in documentation for binaries) is
   not in nep-compress. `plugins/H5Zlz4.c` says `@author Unknown

### 2. `nc_def_var_lz4` / `nc_inq_var_lz4` (`src/nep_compress.c`)

Signatures do not change.

- `nc_def_var_lz4(int ncid, int varid, int level)`:
  - Check order is unchanged: `nc_inq_filter_avail` (`NC_ENOFILTER`),
    then `level` 1-9 (`NC_EINVAL`).
  - Then store
    `unsigned int params[2] = {0, (unsigned int)(1 - level)};` and
    `return nc_def_var_filter(ncid, varid, LZ4_ID, 2, params);`.
  - Add a file-local `#define LZ4_NPARAMS 2` with a Doxygen one-liner.
- `nc_inq_var_lz4(int ncid, int varid, int *lz4p, int *levelp)`:
  - Look up the count first, as now. `NC_ENOFILTER` gives `*lz4p = 0`
    and `NC_NOERR`; set `*lz4p = 1` once found.
  - Return `NC_EFILTER` for `nparams` other than 1 or 2, without
    writing `*levelp`.
  - Read into `unsigned int params[2]`.
  - `nparams == 1`: level = `(int)params[0]`.
  - `nparams == 2`: `int e = (int)params[1];`
    - `e == 0 || e == 1`: level 1
    - `e < 0 && 1 - e <= 9`: level `1 - e` (`e >= -8`)
    - otherwise: `NC_EFILTER`, `*levelp` not written
  - Write `*levelp` only on success.
  - `e` comes from an `unsigned int` cast to `int`. That is
    implementation-defined in C but is two's complement on every target
    we build for, and it matches upstream's own `(int)cd_values[1]`.
    Use the same cast; no extra handling.
