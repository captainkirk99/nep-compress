# V1.3.0 Sprint 2: Add JPEG-LS HDF5 Filter Code

Source: docs/roadmap.md, "V1.3.0 Include JPEG-LS Filter Code / Sprint 2".

## Goal

nep-compress builds and installs its own JPEG-LS HDF5 plugin (filter
32018, "FCIDECOMP") from vendored EUMETSAT fcidecomp sources linked
against CharLS 2.x, the same way it already builds and installs the
vendored HDF Group LZ4 plugin. No external plugin and no system CharLS
package is needed: the plugin lands in `build/plugin` for the tests and
in `<prefix>/lib/plugin` on install. The C and Fortran JPEG-LS API from
1.2.0 is unchanged, so files written by this plugin are byte-compatible
with EUMETSAT FCI files and readable by the fcidecomp and hdf5plugin
providers. The docs say clearly that the filter code comes from the HDF
Group / EUMETSAT fcidecomp project and CharLS, and that the code is
vendored only until those packages are available on Spack and conda.

## Decisions

| Topic | Decision |
| --- | --- |
| Plugin source | Build `plugins/H5Zjpegls.c` (the EUMETSAT fcidecomp `fcicomp-H5Zjpegls` sources, filter 32018). Vendor the rest of the fcidecomp files it needs (`fcicomp-common`, `fcicomp-jpegls`) from the upstream repo `gaubert/fcidecomp-open-repo` (Apache-2.0). Delete the unrelated scratch file `plugins/h5z_jpegls.c` (ID 32012, incompatible parameter layout, never committed). (Ed: use `/fast/ed/nep-compress/plugins/H5Zjpegls.c`) |
| CharLS | ~~Pin CharLS 1.x~~ → **CharLS 2.x as an external dependency** (`find_package(charls 2.1 CONFIG)`, header/library fallback). Updated during implementation: upstream `main` has already ported `fcicomp_jpegls.c` to the CharLS 2.x legacy C API (still pure C), CharLS 1.x cannot decode multi-component `ILV_NONE` streams it encodes, and CharLS 2.x is packaged everywhere (`libcharls-dev`, conda-forge `charls`, Spack). CharLS is not vendored. (Ed: 2b, revised) |
| Plugin dir | Drop `NEPCOMPRESS_JPEGLS_PLUGIN_DIR` and the configure probe. The plugin is built into `${PROJECT_BINARY_DIR}/plugin` like `h5lz4`, and JPEG-LS tests use that directory. (Ed: 3a) |
| Recipes | No Spack or conda recipe changes this sprint; deferred. The recipes also need no `depends_on charls` later because CharLS is vendored, not linked externally — that follow-up only has to cover the `jpegls` variant and installed plugin file. (Ed: 4c) |
| Layout | Vendored JPEG-LS code goes in `plugins/fcidecomp/` (subdirectory, not flat in `plugins/`), so Doxygen can exclude it with one pattern and the provenance is obvious. The files already copied to `plugins/` (`H5Zjpegls.c`, `H5Zjpegls.h`, `H5Zjpegls_definitions.h`, `H5Zjpegls_messages.h`) move there. |
| C API | Unchanged. `nc_def_var_jpegls` / `nc_inq_var_jpegls` and the Fortran wrappers keep their 1.2.0 signatures and semantics (9-parameter user form, 13-parameter stored form). |
| Version / ABI | `VERSION 1.3.0` already set. `SOVERSION 1` stays: the library's ABI does not change (the plugin is a separate module). |
| Missing-plugin test | `jpegls_missing_plugin` keeps its current mechanism: `HDF5_PLUGIN_PATH` points at an empty build directory, `nc_def_var_jpegls` must return `NC_ENOFILTER`. |

### 2. CharLS 2.x dependency (supersedes the original vendoring item)

CharLS 2.x is an external dependency, not vendored: upstream
`fcidecomp-open-repo` `main` (commit
`64ecbb39c4768dac0855b32a13b02441df1cfed2`, the vendoring pin) already
ported `fcicomp_jpegls.c` to the CharLS 2.x legacy C API
(`JpegLsEncode`, `JlsParameters` from `charls/charls.h`). Reasons for
the change, found during implementation:

- CharLS 1.x encodes multi-component `ILV_NONE` images it cannot
  decode (verified: 16-bit, components ≥ 2, `ilv = 0`), which broke
  `tst_jpegls`'s rank-3 case. CharLS 2.x decodes them correctly — no
  patch needed, vendored files stay byte-identical to upstream.
- CharLS 2.x is packaged on conda-forge (`charls`), Debian/Ubuntu
  (`libcharls-dev`) and Spack; CharLS 1.x is packaged nowhere.
- With CharLS linked, not compiled in, the plugin is pure C — no CXX
  needed.

Upstream builds the filter with `LOGGING` defined (its no-logging code
path does not compile), so the target gets `LOGGING`; default level is
`ERROR_SEVERITY`.

### 3. CMake: build and install the plugin

`CMakeLists.txt`:

- Option text: `option(NEPCOMPRESS_BUILD_JPEGLS "Build the JPEG-LS (ID
  32018) API and vendored HDF5 plugin" OFF)` — drop "requires an
  external EUMETSAT fcidecomp HDF5 plugin".
- Delete the `NEPCOMPRESS_JPEGLS_PLUGIN_DIR` cache variable and the
  whole 32018 probe block (lines 72-77).
- Replace it with, after the `h5lz4` block:

  ```cmake
  if(NEPCOMPRESS_BUILD_JPEGLS)
      find_package(charls 2.1 CONFIG)
      if(NOT charls_FOUND)
          find_library(CHARLS_LIBRARY charls)
      endif()
      find_path(CHARLS_INCLUDE_DIR NAMES charls.h PATH_SUFFIXES charls)
      add_library(h5jpegls MODULE
          plugins/fcidecomp/H5Zjpegls.c
          plugins/fcidecomp/fcicomp_log.c
          plugins/fcidecomp/fcicomp_jpegls.c)
      target_include_directories(h5jpegls PRIVATE
          plugins plugins/fcidecomp ${HDF5_INCLUDE_DIRS} ${CHARLS_INCLUDE_DIR})
      target_compile_definitions(h5jpegls PRIVATE LOGGING)
      target_link_libraries(h5jpegls PRIVATE charls|${CHARLS_LIBRARY} ${HDF5_LIBRARIES})
      # BUILD_RPATH also covers the CharLS lib dir.
      install(TARGETS h5jpegls LIBRARY DESTINATION ${CMAKE_INSTALL_LIBDIR}/plugin)
      install(FILES plugins/COPYING.fcidecomp DESTINATION ${CMAKE_INSTALL_DOCDIR})
  endif()
  ```

- The plugin is pure C (CharLS is a linked library), so no
  `enable_language(CXX)`. `LOGGING` matches upstream's build (default
  `ERROR_SEVERITY` — only errors reach stderr).
- Tricky cases:
  - `H5Zjpegls.c` includes `<fcicomp_jpegls.h>`,
    `"fcicomp_log.h"`, `"fcicomp_options.h"`, `"fcicomp_errors.h"` —
    all satisfied by `plugins/fcidecomp` on the include path.
  - `fcicomp_jpegls.c` includes `"charls.h"` — satisfied by
    `CHARLS_INCLUDE_DIR` (`<prefix>/include/charls`) on the include
    path.
  - `fcicomp_log.c` writes to stderr at `ERROR_SEVERITY`; that is
    upstream behavior and stays (the plugin is `H5Z_FLAG_OPTIONAL`
    internally, matching upstream `set_local`).
  - The module exports only the `H5PLget_plugin_*` entry points plus
    the fcidecomp/CharLS symbols; no symbol filtering is needed
    (matches `h5lz4`).
  - `NEPCompressConfig.cmake.in` needs no change: CharLS is compiled
    in, not a link dependency.

## Verification

Local (NetCDF-C `/usr/local/netcdf-c`, HDF5 `/usr/local/hdf5-2.1.1`):

```sh
export LD_LIBRARY_PATH=/usr/local/hdf5-2.1.1/lib:/usr/local/netcdf-c/lib:/usr/local/netcdf-fortran/lib
cmake -S . -B build-jls -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_PREFIX_PATH="/usr/local/netcdf-c;/usr/local/netcdf-fortran;/usr/local/hdf5-2.1.1" \
  -DHDF5_ROOT=/usr/local/hdf5-2.1.1 \
  -DNEPCOMPRESS_BUILD_JPEGLS=ON -DNEPCOMPRESS_BUILD_BZIP2=ON \
  -DNEPCOMPRESS_BZIP2_PLUGIN_DIR=$HOME/plugins/bzip2-only \
  -DNEPCOMPRESS_ZSTD_PLUGIN_DIR=$HOME/plugins/zstd-only \
  -DNEPCOMPRESS_REFERENCE_LZ4_PLUGIN_DIR=$HOME/plugins/lz4-upstream
cmake --build build-jls -j8
ctest --test-dir build-jls --output-on-failure
```

Must pass: `tst_jpegls`, `jpegls_missing_plugin`, `ftst_nep_jpegls`,
plus the whole existing suite. `build-jls/plugin/libh5jpegls.so` must
exist and `ldd` on it must show no `libcharls` (it is compiled in).

Docs:

```sh
cmake -S . -B build-docs -DNEPCOMPRESS_BUILD_DOCS=ON \
  -DNEPCOMPRESS_DOCS_WARN_AS_ERROR=FAIL_ON_WARNINGS
cmake --build build-docs --target docs
```

CI: every `jpegls: "ON"` job (`bzip2-fortran`, `both-fortran`,
`lz4-c-asan`) must configure without `NEPCOMPRESS_JPEGLS_PLUGIN_DIR`,
build `h5jpegls`, and pass ctest including the ASan job.
